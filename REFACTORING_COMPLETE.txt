1. ROUTES: Platform-specific → Domain-organized
   ────────────────────────────────────────────
   ❌ /api/v1/bis/...
   ❌ /api/v1/ekyc/...
   ✅ /api/v1/auth/
   ✅ /api/v1/anomalies/
   ✅ /api/v1/entities/
   ✅ /api/v1/rules/
   ✅ /api/v1/profiles/
   ✅ /api/v1/accounts/
   ✅ /api/v1/configuration/
   ✅ /api/v1/profile/

2. AUTHENTIFICATION: Legacy endpoints → Single generic endpoint
   ──────────────────────────────────────────────────────────────
   ❌ handleGetEkycToken()  }
   ❌ handleGetBisToken()   } → Consolidé en:
   ✅ handleGetSystemToken() (generic, neutre)
   
   ❌ POST /token/ekyc
   ❌ POST /token/system    } → Remplacé par:
   ✅ POST /token (accepts system_id + role)

3. RÔLES: Non-standardisés → Standardisés
   ─────────────────────────────────────────
   ❌ bis, analyste, ekyc (confus, spécifique)
   ✅ admin, analyst, system, reviewer (clair, générique)

4. CODE: Platform-specific → Neutral
   ──────────────────────────────────
   ❌ bisCodeBank → ✅ partnerBankCode
   ❌ isPayeurBIS → ✅ isPayerPartner
   ❌ "Seul le compte BIS" → ✅ "Seul le compte partenaire"
   ❌ "is_bis" JWT claim → ✅ Supprimé (redundant)

5. ORGANISATION: Chaotique → Structurée
   ─────────────────────────────────────
   Fichier server.go réorganisé en 9 sections logiques:
   
   1. PACKAGE & IMPORTS
   2. CONSTANTES & VARIABLES GLOBALES
   3. STRUCTURES PRINCIPALES
   4. MIDDLEWARES D'AUTHENTIFICATION
   5. HANDLERS PUBLICS - AUTHENTIFICATION
   6. HANDLERS PROTÉGÉS (27 handlers × 7 domaines)
   7. INITIALISATION SERVEUR & ROUTES
   8. DEMARRAGE SERVEUR
   9. FONCTIONS UTILITAIRES

POUR COMPRENDRE L'ARCHITECTURE:
  1. Lire: INDEX.md
  2. Puis: SERVER_ARCHITECTURE_DIAGRAM.md
  3. Ensuite: SERVER_STRUCTURE.md
  4. Finalement: Consulter API_ROUTES.md

POUR AJOUTER UN NOUVEL ENDPOINT:
  1. Créer le handler dans server.go (bonne section)
  2. Ajouter documentation Swagger (@Summary, etc)
  3. Enregistrer la route dans NewServer()
  4. Documenter dans API_ROUTES.md
  5. Tester avec le JWT/rôles appropriés

POUR TESTER UN ENDPOINT:
  1. Consulter API_ROUTES.md
  2. Copier la commande cURL
  3. Générer un token: POST /api/v1/auth/token
  4. Exécuter avec Authorization header

POUR DÉPLOYER EN PROD:
  1. go build ./cmd/api
  2. Vérifier compilation sans erreur
  3. Exécuter les tests
  4. Déployer le binaire
  5. Valider les endpoints clés

"C'est à eux de s'adapter pas à moi"

✅ AVANT (Adapté à BIS/eKYC):
   • Routes spécifiques pour chaque partenaire
   • Rôles non-standardisés
   • Logique conditionnelle dans le code
   • Difficile d'ajouter un nouveau partenaire

✅ APRÈS (Neutre et générique):
   • Une seule API générique
   • Rôles standardisés
   • Configuration par paramètres
   • Les partenaires s'adaptent au POST /api/v1/auth/token
   • Facile d'ajouter un nouveau partenaire
